# 需求分析：产物向导与上架引导（Artifact Wizard & Publishing Guide）

> 版本：v1.0 ｜ 日期：2026-10-10 ｜ 状态：待评审
> 本文档是「铸语 PromptForge」从"需求文档工具"演进为"AI 产物工程向导"的需求基线。

---

## 1. 背景与定位

### 1.1 产品演进

现有能力：需求输入 → 单轮澄清问答（≤5 题）→ 生成 Markdown 需求文档。

目标形态：**引导式产物工程向导**——客户用大白话描述需求，系统通过多轮澄清纠正补全信息，生成六种标准 AI 产物之一，并在生成后提供持续优化台，最终引导客户把产物接入到自己的 AI 平台。

```
大白话需求 → 多轮澄清纠正 → 产物生成 → 对话式优化 → 上架公司 AI 平台
```

### 1.2 核心价值主张（GitHub 开源叙事）

- **不是又一个提示词玩具**：产物严格遵循开放标准（Agent Skills 开放标准 / MCP / OpenAI Function Calling / Dify DSL），生成即可用。
- **补齐"最后一公里"**：业界工具止步于生成；本产品提供上架引导 + 交付包导出，让非技术用户也能把产物放进公司 AI 平台。
- **全程可回溯**：澄清轮次、优化轮次、产物版本全部落库，历史页可回放。

### 1.3 名词表

| 名词 | 定义 |
|---|---|
| 产物（Artifact） | 向导最终交付的标准格式文件集（Skill / MCP / Tool / Workflow / CLI / 需求文档） |
| 澄清轮次 | 一轮"AI 提问 → 用户回答"，允许任意多轮（默认上限 5 轮防失控） |
| 优化台 | 产物生成后的对话式修改界面，支持增量改写与版本对比 |
| 交付包 | 按产物类型打包的 zip（含部署说明），可直接导入目标平台 |

## 2. 调研结论（产物格式规范依据）

以下规范均经 2026-10 联网核实，是产物生成的**格式法律**。

### 2.1 Agent Skill（开放标准，agentskills.io）

- 由 Anthropic 发起的开放标准，已被 Claude Code、OpenAI Codex CLI、Gemini CLI、Cursor、VS Code、GitHub Copilot 等采用。
- **目录结构**（必需 SKILL.md，其余可选）：

```
skill-name/
├── SKILL.md       # 必需：YAML frontmatter + Markdown 指令
├── scripts/       # 可选：可执行脚本
├── references/    # 可选：按需加载的参考文档
└── assets/        # 可选：模板与静态资源
```

- **frontmatter 必填字段**：
  - `name`：1–64 字符，仅小写字母/数字/连字符，不以连字符开头结尾
  - `description`：1–1024 字符，说明"做什么 + 何时用"（平台据此决定是否加载）
- **可选字段**：`license`、`compatibility`（≤500 字符环境要求）、`allowed-tools`、`metadata`（任意键值）
- **设计原则：渐进式披露**——frontmatter 常驻系统提示，SKILL.md 正文按需加载，附属文件再按需读取。生成时必须把"何时使用"写清楚，这是触发关键。

### 2.2 MCP Server 配置（Model Context Protocol）

- 各主机配置同为 `mcpServers` JSON 形状，差异只在文件位置：
  - Claude Desktop：`claude_desktop_config.json`（stdio：`command/args/env`；远程：`url/headers`）
  - Claude Code：项目根 `.mcp.json`（可提交 VCS）+ 用户级 `~/.claude.json`，支持 `${VAR:-default}` 环境变量展开
  - Cursor：`~/.cursor/mcp.json`（全局）或 `.cursor/mcp.json`（项目），热加载
  - VS Code(Copilot)：`.vscode/mcp.json`（键名为 `servers`，注意差异）
- **生成规则**：stdio 服务用 `command + args + env`（npx/uvx 启动），远程服务用 `url + headers`；密钥一律走环境变量引用，禁止明文落配置。

### 2.3 Tool（Function Calling，OpenAI 兼容）

- 定义形状：`{ type: "function", name, description, parameters(JSON Schema), strict }`
- **命名约束**：`name` 仅 `a-z A-Z 0-9 _ -`，≤64 字符
- **strict 模式要求**：`parameters` 必须设 `additionalProperties: false`，且所有属性列入 `required`（strict 子集限制）
- DeepSeek 等 OpenAI 兼容端点同构，可直接复用。

### 2.4 Workflow（Dify DSL 为主格式）

- Dify DSL 是 YAML 工程文件：`kind: app` + `version`（0.6.0 对应 Dify 1.15.x；0.7.0 对应 1.16.x，含 Agent App 包）+ `app.mode`（workflow / advanced-chat / agent）
- 图结构必须有：入口节点 → 连通的处理节点 → 可达的 end/answer 节点；每条边 `sourceType/targetType` 匹配；LLM 节点必须带 `context` 对象（禁用也要 `context: {enabled: false, variable_selector: []}`）
- 引用的每个市场插件都要在顶层 `dependencies` 声明；导出物不含 API Key 等密钥
- 版本策略：不知道目标工作区版本时默认 0.7.0 并声明假设；**不得只改版本号字符串"升级"**

### 2.5 CLI（行业惯例，无强制标准）

- 按 POSIX CLI 惯例生成规格包：命令树、参数/标志表、退出码约定（0 成功 / 1 一般错误 / 2 用法错误）、`--help` 文案、README
- 脚手架可选 Python(click) / Node(commander)，V1.0 先交付"规格文档 + 可选脚手架"，不做真实打包发布。

> 来源：anthropic.com/engineering（Agent Skills）、agentskills.io/specification、platform.claude.com/docs（Skills API）、模型上下文协议各主机配置文档、openai.com（Structured Outputs / Function Calling）、docs.dify.ai（App DSL 导入导出）。

## 3. 用户旅程（四步向导）

### Step 1 需求输入（已有，微调）

- 大白话描述 + **新增：产物类型选择**（六选一，默认"需求文档"；每种类型带一句话说明和示例）
- 不同类型驱动不同的澄清问题模板与产物模板

### Step 2 澄清纠正（升级：单轮 → 多轮）

- FR-2.1 AI 每轮生成 ≤5 个澄清问题（JSON 结构化），用户逐条回答或跳过
- FR-2.2 **多轮**：回答提交后 AI 判断信息是否充分；不充分则给出一轮新问题（默认最多 5 轮），每轮展示"已收集信息卡"让用户看到进展
- FR-2.3 **可回改**：任意历史答案可点击修改，修改后触发受影响问题的重新评估
- FR-2.4 **主动补漏**：用户可随时补充自由文本信息，AI 融合进信息卡
- FR-2.5 "信息充分"判定：AI 输出 `ready: true/false + 理由`，用户也可无视判定直接进入生成

### Step 3 产物生成 + 优化台（新增优化台）

- FR-3.1 按 SSE 流式生成产物；多文件产物（Skill/MCP/CLI）按文件逐个流式，前端按文件树展示
- FR-3.2 **优化台**：左侧文件树 + 右侧内容预览（Markdown 渲染 / JSON 高亮 / YAML 高亮）；底部对话输入
- FR-3.3 对话式增量改写：用户说"把 description 写得更触发友好"→ AI 只改动涉及文件，返回变更 diff 摘要 + 新版本
- FR-3.4 **版本对比**：任意两个版本并排 diff（按文件），可一键回滚到某版本（回滚也生成新版本，不删历史）
- FR-3.5 每轮优化记录角色/内容/影响的文件，可回放

### Step 4 上架引导（新增）

- FR-4.1 按产物类型 + 用户在 Step 1 可选的"目标平台"生成接入步骤（目标平台未指定时给通用指引 + 常见平台页签）
- FR-4.2 引导内容是**可执行步骤**，不是泛泛而谈：
  - Skill → 目录结构清单 + 各平台安装路径（如 `~/.claude/skills/`）+ 验证方法
  - MCP → 各平台配置文件路径表 + 针对该产物的 `mcpServers` JSON 片段（含 env 占位）+ 重启/验证命令
  - Tool → 接入代码示例（OpenAI/DeepSeek SDK 调用片段）
  - Workflow → Dify 导入步骤（界面路径）+ 版本兼容提示 + 缺插件处理
  - CLI → 安装/使用/退出码说明
- FR-4.3 **交付包导出**：一键 zip（产物文件 + 接入指引 README + 变更日志）；文件名含产物名与版本
- FR-4.4 上架检查清单：按类型生成的 checklist（如 MCP：命令可执行？env 是否齐？工具数 ≤40？），逐项可勾选（仅前端状态）

## 4. 六种产物类型定义

| 类型 | 产物形态 | 格式依据 | 交付包内容 |
|---|---|---|---|
| 需求文档 | 单 Markdown | 内部模板 | README.md + 文档 |
| Agent Skill | 目录（SKILL.md + 可选附属） | agentskills.io 开放标准 | skill 目录 zip + 安装指引 |
| MCP Server | 服务器脚手架（index.ts/server.py + README）+ 配置片段 | MCP 规范 + 各主机配置 | 源码 zip + mcpServers 片段 + 各平台接入表 |
| Tool | function 定义 JSON（可含调用示例） | OpenAI function calling | tools.json + SDK 示例 |
| Workflow | Dify DSL YAML | Dify DSL 0.7.0 | dsl.yml + 导入步骤 + 兼容提示 |
| CLI | 命令规格文档 + 可选脚手架 | POSIX CLI 惯例 | README + 规格表 + 可选 click/commander 模板 |

约束：产物内容中的名称字段必须符合各标准（如 skill name 小写连字符、function name ≤64）；生成后由**后端校验器**做格式校验（命名正则、frontmatter 必填、JSON Schema additionalProperties、DSL version 字段），校验失败前端标黄并给修复建议。

## 5. 数据模型变更

新增 3 张表（沿用现有约定：BIGSERIAL 主键、TIMESTAMP、逻辑外键级联、user_id/project_id/created_at 索引）：

```
artifacts            产物主表
  id, project_id FK→requirement_projects, artifact_type, name,
  target_platform, current_version, status, created_at, updated_at

artifact_files       产物文件（每版本全量快照）
  id, artifact_id FK→artifacts, version, file_path, content,
  created_at
  索引：(artifact_id, version)

optimization_rounds  优化台对话轮次
  id, artifact_id FK→artifacts, round_no, role, content,
  affected_files, result_version, created_at
```

既有表变更：

- `requirement_projects` 增加 `artifact_type VARCHAR(20) DEFAULT 'document'`、`target_platform VARCHAR(30)`
- `requirement_answers` 增加 `round_no INT DEFAULT 1`（多轮澄清）、`question_no INT`
- 澄清"信息充分"判定结果存入 `requirement_projects.status`（新增 CLARIFYING → READY → GENERATING → OPTIMIZING → DONE）

越权规则：artifacts 及其子表一切查询必须 join `requirement_projects.user_id = 当前用户`。

## 6. API 设计（新增部分）

| 方法 | 路径 | 说明 | 权限 |
|---|---|---|---|
| POST | `/api/requirement/projects/{id}/answers` | 请求体增加 `round_no`，返回 `ready` 判定 | 登录+归属 |
| POST | `/api/requirement/projects/{id}/answers/undo` | 回改某轮答案，重算信息卡 | 登录+归属 |
| POST | `/api/requirement/projects/{id}/artifact` | SSE 生成产物（按 artifact_type） | 登录+归属 |
| GET | `/api/artifacts/{id}` | 产物详情（文件树+当前版本） | 登录+归属 |
| POST | `/api/artifacts/{id}/optimize` | SSE 增量优化（对话式） | 登录+归属 |
| GET | `/api/artifacts/{id}/diff?from=&to=` | 两版本 diff（按文件） | 登录+归属 |
| POST | `/api/artifacts/{id}/rollback` | 回滚为当前版本（生成新版本） | 登录+归属 |
| GET | `/api/artifacts/{id}/publish-guide` | 上架指引（按类型+平台） | 登录+归属 |
| GET | `/api/artifacts/{id}/export` | 下载交付包 zip | 登录+归属 |

SSE 载荷沿用现有 JSON 约定（`{delta|file|version|done}`）。

## 7. 提示词模板体系

每类型三套模板 + 公共两套，全部配置化存放于后端 `resources/prompts/`：

- 公共：澄清问题生成（按 artifact_type 换问题域）、信息充分判定（输出 `ready + 理由 + 缺口清单`）
- 各类型：生成模板（含格式规范的硬约束段落）、优化模板（输入=当前文件+对话历史+修改指令，输出=变更文件+diff 摘要）、上架指引模板（输入=产物元数据+目标平台，输出=分步指引）
- 模板内嵌"格式法律"：如 Skill 模板内写死 name/description 约束；Tool 模板内写死 strict 子集规则；Workflow 模板内写死 DSL 版本策略与节点连通规则。

## 12. 开放问题（待用户拍板）

1. 目标平台清单：上架引导先内置哪些？（建议：Claude Code / Claude Web / Cursor / Dify / 通用自建平台，其余走"通用"）
2. MCP Server 产物默认语言：TypeScript 还是 Python？（建议 TypeScript，生态更通用；Python 留模板开关）
3. 优化台是否需要支持"整文件重写"模式（增量改写失败时的兜底）？（建议要）
